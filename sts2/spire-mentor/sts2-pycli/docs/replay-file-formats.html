STS2 Replay File Formats

Two distinct on-disk formats record a Slay the Spire 2 run in this project. This page documents both — field by field, with real examples.

1 · Overview — two formats, one word

The word “replay” is overloaded in this repo. It refers to two completely different files that are produced by different tools, in different shapes, for different purposes:

A · JSONL run logs JSONL

Written by this project as it drives the headless engine. One JSON object per line, alternating state (decision point the engine offered) and action (command we sent back). This is what the Workbench GUI scrubs through.

Producer: python/game_log.py · Location: logs/<ts>_<char>_<seed>.jsonl

B · Scraped .run files JSON

Captured from real human games by the external sts2_run_scraper tool. A single JSON object describing a whole run: acts, per-floor history, choices made, HP/gold snapshots. Consumed by the parity harness to verify the engine reproduces real play.

Producer: external scraper · Parser: python/replay/scraped.py · Location: ../sts2_run_scraper/data/files/<char>/<YYYY-MM>/<uuid>.run

2 · Format A — JSONL run logs logs/*.jsonl

A JSONL ("JSON Lines") file: each line is one self-contained JSON object — a record. Records are appended live (and flush()ed) as the run plays, so a log is readable even mid-run or after a crash. The producer is GameLogger in python/game_log.py; old logs auto-delete after 7 days.

Filename

logs/20260605_035316_Necrobinder_run_5.jsonl
     └── ts ──┘ └────── character ──┘ └seed┘
     %Y%m%d_%H%M%S      Necrobinder    run_5   (slashes in seed → "_")

Record envelope

Every line shares the same four-key envelope; the payload lives in data.

FieldTypeMeaning
stepintMonotonic counter. Incremented on each state; the following action reuses the same number, so a state/action pair shares one step.
tsstringISO-8601 wall-clock timestamp (datetime.now().isoformat()).
typestring"meta" (self-describing header, first line), "state" (engine → us), or "action" (us → engine).
dataobjectThe payload. Shape depends on type + decision/cmd (below).

After the meta header, a log is a strict alternation: state, then the action chosen for it, repeated. A real Necrobinder log of 382 play records is exactly 191 states + 191 actions.

2.0 · meta header — the self-describing first record

Every log's first line is a meta record naming the run, so a log identifies itself without relying on the start_run command (the Workbench live/branching loggers never emit one). Written by GameLogger.__init__.

{"step":0,"ts":"2026-06-06T10:00:00.000000","type":"meta",
 "data":{"character":"Necrobinder","seed":"run_5","ascension":0}}
data fieldTypeNotes
characterstringCharacter the run was started with.
seedstringThe seed string handed to the engine (the real RNG seed it hashes). May be a synthetic label like "run_5" for batch runs, or a game seed like "SYDDKWZUC8".
ascensionintAscension level (0–20). Defaults to 0.
Consumer-safe. TimelineStore.load_jsonl only acts on state/action records, so the meta line is silently ignored by the Workbench timeline — it never shifts step indices.

2.1 · action records

The very first record is always a start_run; every subsequent action is a generic action command with an action verb and its args.

// run bootstrap (carries ascension since it became self-describing)
{"step":0,"ts":"2026-06-05T03:53:16.897153","type":"action",
 "data":{"cmd":"start_run","character":"Necrobinder","seed":"run_5","ascension":0}}

// an event/menu choice
{"step":1,"ts":"...","type":"action",
 "data":{"cmd":"action","action":"choose_option","args":{"option_index":0}}}

// a card play in combat
{"step":17,"ts":"...","type":"action",
 "data":{"cmd":"action","action":"play_card","args":{"card_index":0,"target_index":0}}}
data.cmdOther keysWhen
start_runcharacter, seed, ascensionFirst action record (after the meta header). ascension is included by all drivers.
actionaction (verb), args (object)Every other step. Common verbs: choose_option (option_index), play_card (card_index, target_index), plus map / reward / rest selections.

2.2 · state records

A state payload always has type:"decision" and a decision discriminator naming the kind of choice being requested, plus a context block locating the run (act, floor, room, boss). Observed decision values in one run:

decisionMeaning
combat_playMid-combat: pick a card to play (or end turn). The richest state — carries hand, enemies, piles, powers.
map_selectChoose the next room on the act map.
card_rewardPick (or skip) a card from a reward screen.
card_selectSelect card(s) from a pile (e.g. discard/exhaust effects).
event_choiceChoose an event/Neow option.
rest_siteRest-site action (rest / smith / …).
game_overTerminal record — run ended (win or death).

Shared context block

"context": {
  "act": 1, "act_name": "Overgrowth",
  "floor": 2, "room_type": "Monster",
  "boss": {"id": "CEREMONIAL_BEAST_BOSS", "name": "Ceremonial Beast"}
}

Reading a log in Python

import json
with open("logs/20260605_035316_Necrobinder_run_5.jsonl") as fh:
    records = [json.loads(line) for line in fh]

for r in records:
    if r["type"] == "state":
        print(r["step"], r["data"]["decision"], r["data"]["context"]["floor"])
    else:
        print(r["step"], "→", r["data"].get("action", r["data"]["cmd"]))

3 · Format B — Scraped .run files JSON

A .run file is a single JSON object describing one complete human-played run, produced externally by sts2_run_scraper. The parity harness parses it (python/replay/scraped.py → parse_run()) into typed Run / Floor dataclasses, re-drives the same choices through the Rust engine, and asserts the engine's HP / gold / deck match the recorded snapshots.

Schema pin. The parser targets sts2_run_scraper schema v0.103.2. It is lenient about unknown fields (forward-compatible) but strict about the fields it actually reads. Example files in the corpus may carry an older build_id (e.g. v0.98.3) — the harness filters to the pinned build.

Filename & location

../sts2_run_scraper/data/files/the-defect/2026-03/05eeee23-5bf5-4327-a1e4-166a03708495.run
                               └ character ┘└YYYY-MM┘ └──────────── uuid ─────────────┘

3.1 · Top-level object

Observed keys of a real .run file:

{
  "schema_version": ...,
  "build_id": "v0.98.3",
  "seed": "SYDDKWZUC8",
  "ascension": 1,
  "game_mode": ...,
  "platform_type": ...,
  "modifiers": [...],
  "acts": ["ACT.UNDERDOCKS", "ACT.HIVE", "ACT.GLORY"],
  "players": [ ... ],                 // length 1 = single-player (required)
  "map_point_history": [ [...], [...], [...] ],   // one array per act
  "win": true,
  "was_abandoned": false,
  "killed_by_encounter": ...,
  "killed_by_event": ...,
  "start_time": ...,
  "run_time": ...
}
FieldTypeParsed intoNotes
seedstringRun.seedRaw human-typed alphanumeric seed, e.g. "SYDDKWZUC8". The engine's …from_string_seed applies the same string-hash mix the C# game uses.
ascensionintRun.ascension0–20, passed to the engine constructor verbatim.
build_idstringRun.build_idGame build the run was recorded on.
winboolRun.wonDid the human win (final-act boss kill)?
actsstring[]Run.actsPer-act biome ids; same length as map_point_history.
playersarray—Must be length 1. Multiplayer runs raise ValueError — the harness is single-player only at this pin.
map_point_historyarray of arraysRun.floorsOuter = acts, inner = floor rows. Flattened in encounter order (Act 1 → 2 → 3). Must be non-empty.

3.2 · A floor row

Each inner element of map_point_history is a floor row with keys map_point_type, player_stats, rooms. The harness reads the first two.

FieldTypeNotes
map_point_typestringRoom type, lowercased on parse: ancient / monster / elite / boss / shop / rest_site / treasure / event.
player_statsarraySingle-player ⇒ index [0] is the snapshot. Must be present — a missing entry is a scraper drop signal and raises ValueError.
roomsarrayMap geometry; not consumed by the harness.

Floors are 1-indexed across the whole run (ancient room = floor 1, boss = final). The Floor.ordinal the parser assigns is a global running count, not per-act.

3.3 · player_stats[0] — the per-floor snapshot

This is the "after this floor resolved" state. Observed keys: ancient_choice, cards_gained, current_gold, current_hp, damage_taken, event_choices, gold_gained, gold_lost, gold_spent, gold_stolen, hp_healed, max_hp, max_hp_gained, max_hp_lost, player_id, relic_choices.

3.4 · How parse_run() maps it to a Floor

The parser flattens the messy, room-type-dependent scraper shapes into a uniform Floor dataclass:

Floor fieldSourceExtraction rule
ordinalpositionGlobal 1-indexed running count across all acts.
map_point_typerow.map_point_typeLowercased.
hp_aftercurrent_hpExact for non-combat; combats allow ±2 tolerance (Vulnerable rounding / intent variance).
gold_aftercurrent_goldAlways exact.
relics_pickedancient_choice + relic_choicesUnion of entries with was_chosen/was_picked true. Normalized to "RELIC.<UPPER_SNAKE>" (prefix added if missing).
cards_gainedcards_gainedCard ids added to the master deck (shop buys, reward picks, event grants).
cards_removedcards_removedRemovals (Smith pre-state, shop purge, event removals).
upgraded_cardsupgraded_cardsOne entry per upgraded instance. Bare strings in v0.103.2; the parser also accepts {id} dicts.
event_choicesevent_choicesFor chosen options, the TextKey tail is lowercased (e.g. …options.BOTTLE.title → "bottle").
raw_player_statswhole blobRetained verbatim for diagnostics; not used in equality/checkpoints.
Shape quirks the parser absorbs. card_choices entries are {card:{id}, was_picked}; relic_choices are the same with relic/was_chosen; ancient_choice (floor 1 only) uses {TextKey, was_chosen} directly. cards_gained/cards_removed entries are {"id": "CARD.X"} dicts, while upgraded_cards are bare "CARD.X" strings. The helper _ids() accepts both string and {id} forms so the parser keeps working if the scraper schema converges either way.

Parsing a .run in Python

from pathlib import Path
from replay.scraped import parse_run

run = parse_run(Path(".../the-defect/2026-03/05eeee23-….run"))
print(run.seed, run.ascension, "won" if run.won else "lost")
for f in run.floors:
    print(f"{f.ordinal:>2} {f.map_point_type:<9} hp={f.hp_after} gold={f.gold_after} "
          f"+cards={f.cards_gained} +relics={f.relics_picked}")

The Run dataclass exposes: seed, ascension, build_id, won, acts, floors[], source_path. Each Floor: ordinal, map_point_type, hp_after, gold_after, relics_picked, cards_gained, cards_removed, upgraded_cards, event_choices, raw_player_stats.
