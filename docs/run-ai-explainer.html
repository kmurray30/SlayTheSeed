How the Run-AI decides

MCTS, the value net, the ranker, and the heuristics — what each one is for, when it fires, how long it takes, and why we built it that way.

HISTORICAL — describes the pre-PPO architecture.

The pick-ranker stack was removed on 2026-07-12 and the value net was turned off in the v0.107.1 retrain (V-pathing measured net-negative, +9.2pp with it OFF). Every out-of-combat decision is now made by a per-character PPO transformer champion; combat is still MCTS. Win-rates quoted below also predate honest search (landed 2026-07-12, worth about −22.8pp) and are not comparable to current numbers. Its engine timings (transitions/sec, searches/sec, combat costs) date from mid-2026 as well and predate the October 2026 engine speed-up; the current figures are on the documentation site. Kept as the clearest surviving explanation of the tiered-decision design and the reasoning behind it.

TL;DR

There is one rule for combat and one rule for everything else.

In combat → always simulate

Every combat decision runs chance-node MCTS (1000 sims, 4000 at bosses). No learned net picks the move; the search does. Leaf states are scored by a fast hand-tuned heuristic. There is no "is the net confident?" shortcut here.

Out of combat → heuristic first, simulate only when unsure

Card rewards, smith, deck edits, relics, paths, rest: scored instantly by a heuristic value function V. If the top-2 are close (low margin), we escalate to short combat rollouts. The ranker is a learned shortcut that replaces those rollouts on card choices.

Where the "ranker vs sims" gate actually lives. The "not sure → simulate" decision keys off the heuristic value function's top-2 margin — not the ranker's confidence. The ranker is either (a) the sole decider on card surfaces with no sim fallback (--policy ranker), or (b) a candidate pre-filter that narrows which moves the already-triggered sims evaluate (--policy tiered + prefilter).

The big-picture map

Every decision the agent faces is routed by a single fork: is this a combat decision or a meta decision? policy/mod.rs:151-267

① Combat — MCTS, every time

When the engine hands the agent a combat decision, it builds a fresh search tree over a clone of the combat state and runs Monte-Carlo Tree Search. There is no learned policy gate: the search is the decision. policy/mod.rs:200-251

Tree policy

Classic UCT: Q + c·√(ln N / n), c=√2. Default mode is chance nodes (DPW + expectimax over stochastic draws/shuffles), matching the real game's randomness. sts2-mcts/src/lib.rs:21,317,330

Leaf evaluation

At the depth cap, a hand-tuned heuristic scores the state — the wide 172-feature Texel evaluator (TexelWide), not a learned net. Terminal loss is clamped to −0.9. value_net.rs:1737-1750

Rollout depth = 200

Engine default is 10 — which truncated act-1 fights before they ended and was the 2026-06-12 win-rate floor. At depth 10 a fight bleeds 13 HP; at 200 it bleeds 3. policy/mod.rs:76-83

How the move is finally chosen

After search_n(sims), the root child is picked by mean value, then visits — except a lost-position override fires first: if every move looks lost, prefer dealing damage / clearing Slippery over a suicidal EndTurn. policy/mod.rs:200-251 · lib.rs:1152-1204

Why MCTS and not a learned combat policy? Combat is where the real complexity (and variance) lives, and the engine simulates fast (~1.4–1.5M transitions/sec). Search over the true rules is the strongest signal we have — so in combat we pay for it directly. Learned value nets exist as optional leaf evaluators but are not what the deployed budgets use.

② Meta decisions — the tiered stack

A whole 3-act run has only ~60–100 meta decisions, almost all with ≤4 options. So the search space is trivial — what matters is evaluation quality. The design funnels combat (the ground truth, but slow) into offline labels and a thin, uncertainty-gated runtime escalation. docs/plans/2026-06-12-full-run-ai-plan.md:205-215

The margin gate

Tier 1 returns scores; the margin is simply top1 − top2. heuristic.rs:68-77 If that margin clears the per-surface threshold, the heuristic is confident and we stop. Otherwise we escalate. Thresholds live in data/runai/heuristic_v.toml [tiers]:

↳ Card-reward decisions, end to end

The rollout score that breaks the tie blends outcomes: win − loss + 0.002·dmg − 0.004·hp_lost — winning dominates, then HP economy, then tempo. rollout.rs:441-449

↳ Pathing decisions

Pathing does not use the card machinery. Every floor it enumerates all paths from the current node to the boss (no pruning, cap 10k), walks each through a cheap projection model, scores V(projected state at boss arrival) + per-room terms, and commits only the first edge of the best path — then replans next floor. surfaces/pathing.rs:1-11,31-72

The projection model

Not a per-fight rollout. A table-based walk: expected HP loss per room (monster 8/12/16, elite 18/26/34 by act), gold, reward ΔV, rest = max(heal, smith), events as uniform chance nodes. Boss rooms deliberately excluded — we evaluate V at boss arrival. projection.rs:64-112

Optional V-pathing

With a value net attached, map edges can instead be ranked by V(projected economy). There is also a built path_delta probe that simulates the one committing edge's next encounter — but it's gated off by default (path_margin = 0): measured, no headroom. ranker.rs:102-115 · rollout.rs:994-1089

Why enumerate instead of search? The map is a tiny DAG and V is cheap, so exhaustive enumeration is affordable and exact. The hard part isn't search — it's "what is V at a future node?", which is undefined without a model of how HP/gold/deck evolve along the way. That's what the projection model supplies. projection.rs:7-9

The ranker, precisely — what is its function?

The ranker is a learned shortcut that replaces expensive rollouts on card-shaped choices. It is trained to imitate what the tier-2/3 simulations would have decided, so at runtime you get rollout-quality card picks at near-zero cost.

Architecture — listwise MLP, ~1M params

Context encoder: 1477-dim run-state → Linear(1477→512) + ReLU.

Per-candidate head: [512 context ⊕ 64-dim card embedding ⊕ 5 candidate scalars] → Linear→64→ReLU→Linear→1. One scalar score per option; policy takes argmax. eval/ranker.rs:303-403

Input features

Context (1477): deck histogram [count, upgraded] per card (1158) + relic multi-hot (294) + 25 scalars (HP, gold, act, boss proximity, ascension, deck stats…) incl. a boss-identity one-hot. Built only from a VisibleRunView — no peeking. ranker_features.rs:318-387

Candidate (5): upgraded flag + one-hot {Add, Remove, Upgrade, Skip}, plus the 64-dim embedding of the card. ranker_features.rs:244-302

What it's trained on

The deployed ranker_chain500 learns the rollout oracle's preference order via listwise softmax cross-entropy. The label per option is its chain_delta rollout score — survival of a chained [normal×2, elite, boss] sequence with HP carryover (a non-myopic attrition signal), with the per-move probe search itself being chance-node MCTS to match the deployed combat search.

  • Coverage: card rewards (incl. Skip), deck remove / upgrade / transform, smith picks.
  • Not covered → falls back to heuristic: boss/shop relics, gold, potions, pathing, events, rest, combat. ranker_features.rs:287-291
  • Two roles: sole decider (--policy ranker, argmax, no sim fallback) or a tier-2 pre-filter that picks which candidates get probed (--policy tiered). tiered.rs:64-71,177-188
Why a ranker at all? The honest evaluator is the rollout — but it costs ~0.5 s/decision. The ranker distills ~66k rollout labels into a forward pass that's effectively free, so card picks get rollout-grade judgment everywhere, not just on the few decisions we can afford to simulate live. full-run-ai-plan.md:214-215

The value net — "how far will this run get?"

Architecture

Simpler than the ranker: same 1477-dim context, no card embedding/head. standardize → Linear(1477→256) + ReLU → Linear→1 → ·σ+µ. Single scalar output. eval/run_value.rs:239-264

What it predicts

The deployed value_human_a0 predicts acts_reached + win (win-aware graded return), trained on the spire-codex human corpus. Pure win/loss is unusable at ~0% wins, so "act reached" is the graded learning signal. train_value.py:1-19

Where it's used: ranking map edges (V-pathing), re-ranking the ranker's top-N card picks by V(resulting state) (the "act-3 wall" refinement), and as a shop oracle. ranker.rs:102-160

Why we made each choice

Why split combat vs meta?

They have opposite shapes. Combat: huge branching, fast simulator → search wins. Meta: ~60–100 decisions, ≤4 options each → search is free, so evaluation quality is everything. One mechanism can't be best at both.

Why heuristic-first with a margin gate?

Simulating every meta decision would cost minutes/run for no benefit — most picks are obvious. Spend the expensive rollouts only where the cheap evaluator is genuinely unsure (small top-2 margin). "Thin uncertainty-gated escalation."

Why gate on the heuristic margin, not ranker confidence?

The margin is a property of the value landscape (how close the options are), which is exactly the question "is this decision pivotal?". A net's softmax confidence is not calibrated to that, and the ranker doesn't even cover all meta surfaces.

Why a learned ranker if rollouts are the ground truth?

Rollouts are ~0.5 s each — too slow to run on every card pick. The ranker distills ~66k rollout labels into a free forward pass, so every card pick gets rollout-grade judgment, not just the escalated few.

Why chance-node MCTS (vs single-determinization)?

It models the game's real stochasticity (draws, shuffles) via expectimax instead of pretending one fixed shuffle. It's also the default the deployed labels were trained against — train/deploy consistency.

Why "act reached" as the value target?

At ~0% win rate a pure win/loss label is almost all zeros — no gradient. Final act ∈ {1,2,3} (+win) is a graded signal that still tracks run health, so the net learns something useful before win rate climbs.

Why enumerate paths instead of searching?

The map is a small DAG and V is cheap, so full enumeration is exact and affordable. The real difficulty is defining V at future nodes — solved by the projection model, not by more search.

Why are Path/Rest probes built but turned off?

They were measured (E2 said Path/Rest own the act-2 frontier) but the live probes showed no win-rate headroom yet, so they're gated off (margin = 0) pending better calibration (E12/E13). Build, measure, demote.

The one-sentence design thesis (from the plan): combat simulation is the ground truth but too slow to be the runtime evaluator, so it is funneled into (a) offline labeling/calibration and (b) a thin uncertainty-gated runtime escalation path. Everything above is a consequence of that sentence.
